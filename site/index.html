Dependency management that explains itself.

DX is a Cargo-compatible tool for Rust projects: it shows what a change introduces before it lands, runs security before any build script executes, and makes every change recoverable.

Cargo-compatible security-first explainable recoverable MIT OR Apache-2.0 
$ dx add serde@1 --features derive --plan
NEW packages in the graph (7): serde (direct) + 6 transitive
EXECUTION surfaces during the build: build.rs in 4 crates; proc-macros: serde_derive
MSRV required by new packages: >= 1.71
Security (candidate graph): no known findings · Decision: APPROVED
(plan: nothing was written.)
DX reuses Cargo and rustc for resolution and compilation. It does not replace them — it adds a layer of explanation, security and recovery on top. The executable is dx; the published crate is dx-cli.

Why DX

Cargo is already a solid package manager. The gap DX targets is the fragmentation of experience and guarantees across many good tools. DX composes them and answers three questions a change should answer:

What am I introducing?

New transitive crates, activated features, MSRV bumps, and every build.rs/proc-macro that will execute during the build.

Is it safe to build?

Advisories, licenses and sources are evaluated on the candidate graph before anything is compiled or landed.

Can I undo it?

Journaled, atomic changes and a validate-or-restore update flow: a failed step never leaves a broken project.

Install

DX needs a Rust toolchain. Optional scanners cargo-audit and cargo-deny enable the full security gate.

# From source (clone the repo)
$ git clone https://github.com/ngolacloud/dx && cd dx
$ cargo install --path crates/dx-cli      # installs the `dx` binary

# Recommended scanners for the security gate
$ cargo install cargo-audit cargo-deny
Not yet published to crates.io. The dx crate name is taken; the intended published name is dx-cli.

Quickstart

$ dx new my-api --bin
$ cd my-api
$ dx add serde@1 --features derive --plan   # preview impact, nothing written
$ dx add serde@1 --features derive          # resolve → gate → land if approved
$ dx why serde_derive                       # who pulls this crate?
$ dx update --security                       # which advisories would an update clear?
$ dx test --suite unit --format junit --out report.xml
$ dx build --release

Explainable changes

dx add --plan resolves the candidate graph in an isolated staging area (via cargo generate-lockfile, without running build.rs) and reports the impact: new direct/transitive packages, execution surfaces, MSRV, the security verdict, and cache-vs-new downloads — without touching your manifest.

dx why <crate> and dx explain --duplicates|--feature answer graph questions, confirmed by Cargo's own resolution.

Security before execution

The gate runs on dx add and dx update: resolve the candidate graph without running code, evaluate it with cargo-audit (advisories) and cargo-deny (licenses, sources, bans), and only then land it.

LayerQuestion
IntegrityDo the bytes match the pinned artifact? (dx fetch)
SourceIs this registry/repository allowed? (no silent fallback)
VulnerabilitiesAny applicable advisories? (CVE or not)
ExecutionWhat runs during the build? (build.rs, proc-macros)
IsolationWhat can it reach? (dx build --isolated: network off, env scrubbed)
Decisions are cached and keyed by graph + policy + advisory snapshot + scanner. A new advisory invalidates an old verdict even if the downloaded bytes are intact. An expired advisory base blocks use (pending), not the download. Absence of findings is not proof of benignity.

Predictable recovery

Mutations produce a plan first (--dry-run), write atomically with a journal (crash-safe), and serialize concurrent runs with a workspace lock. dx update --apply validates with the gate (and --test) and restores the previous lockfile if validation fails.

Honest limits

  • DX is a layer over Cargo; invoking cargo directly bypasses the DX gate — by design. CI and a controlled build environment enforce policy.
  • Impact analysis and the pre-landing gate cover self-contained manifests; workspace/path shapes land as unverified (run dx audit).
  • Build isolation enforces network/env/limits; filesystem isolation is not enforced yet and is reported as such.
  • Bundles are verifiable, not byte-for-byte reproducible.
  • No “zero CVEs” claims: findings are relative to a dated advisory snapshot.
